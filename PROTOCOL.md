# Lesson protocol

**DRAFT 2026-09-24 (#6). Ben reviewed it on 09-24 and accepted the proposed rules; what remains is pending in other issues.** Written from
`notes/protocol-decisions.md` and `notes/protocol-inputs-2026-09-24.md`. Every rule
is marked by its standing:

- no mark: decided with Ben (the issue number says where);
- **[pending #n]**: waiting on a decision in that issue.

Once nothing is marked, this file replaces `notes/protocol-decisions.md` as the
record.

This protocol is for Claude drafting lessons. It uses fixed counts and ends with a
checklist that a lesson must pass before its `status` in `lessons.yml` becomes `done`.

---

## 1. Workflow

1. **Outline.** Every lesson gets an outline, `outlines/<id>.md`, before any lesson is
   drafted (optional lessons too). Copy `outlines/_template.md`; `outlines/rasch.md` is
   the worked example. Ben reviews outlines module by module (#8).
2. **Cross-check.** Iterative passes over all the outlines: every hook paid off or
   flagged unpaid; every pick-up introduced in an earlier lesson; duplication; gaps.
   One report per pass for Ben; repeat until clean (#9). A **depth pass** ranks the
   Go deeper candidates by how many lessons pick them up; Ben cuts the short list (#10).
3. **Record threads.** The agreed cross-lesson connections go into `lessons.yml` as
   `threads:` (§4). The build checks them.
4. **Draft.** Draft from the outline, after reading every thread that touches the
   lesson (§4). Mark the lesson `status: draft`.
5. **Review.** Run the checklist (§9). Anything only Ben can decide goes into pinned
   issue #62 with the `needs-ben` label. Mark the lesson `done` when the checklist passes
   and Ben has signed off.

Curriculum changes (splitting a lesson, moving an idea between lessons, changing
prerequisites) are made at the outline stage, not while drafting.

---

## 2. Principles

- **A first course.** Core lessons stay at first-course level. Deeper material is
  either an optional lesson or a collapsible callout.
- **Widgets, then simulation, then data.** Each lesson moves from interactive widgets
  (build intuition) to a simulation in webR (generate data from the model and recover
  it) to real IRW data (see what happens when the model meets the world).
- **The real-data section finds something.** Choose tables for what they teach: an
  item that misfits, a keying problem you can't see in the data, a "how many factors"
  answer that differs from the design. Write the prose around the actual output. Never
  assert a pattern the output doesn't show.
- **Lessons are in conversation.** An idea introduced in one lesson is returned to,
  tested, relaxed or shown to fail in later ones. The outline and threads make these
  connections explicit.
- **Broad data, always cited.** Draw on a broad swathe of the IRW rather than a few
  familiar tables, and always cite and link the original data source, not only the
  IRW table (§5).
- **Gentle about the data.** Never be especially critical of the empirical data we
  use. These datasets were shared by people who did the hard work of collecting
  them. Note issues (missing responses, a keying problem, an item the model doesn't
  describe) plainly and gently, as facts about fit or design, not as faults in the
  data or its authors. A "failure case" is a case where the *model* fails.
- **Show, don't assert.** When the text says
  what software does ("`mirt` fixes the mean ability at 0"), show it in a small example.
  When it mentions a result from the literature (the 1.7 scaling constant), cite and
  link the source.
- **Written in Ben's voice** (§6).

## 3. Lesson anatomy (#2)

### Section order

Fixed, all required, as H2 headings in this order:

| Section | What goes in it |
|---|---|
| *(header box)* | Generated by `lesson_header()`: module, prerequisites, next lessons, threads, and a note that the lesson was written largely by Claude (#70). |
| What this is for | One paragraph. Opens on the verdict or the problem, not on a definition. Picks up from the prerequisite lesson. |
| Goals | "By the end of this lesson you should be able to:" and 4–6 bullets, each something the reader can do. |
| Core ideas | One H3 per core idea from the outline. "Try it" widgets (H4) inline; quick checks after the major subsections; collapsible depth callouts. |
| Simulate | A webR cell that generates data from the model, fits it and compares with the truth; what to change and what to watch for; a download link. |
| With real data | IRW tables (§5), with code folded but shown; the one predict-then-check; the finding the section is built around. |
| Problems | 6 problems (§5). |
| Ask Claude | Generated by `ask_claude()` in `_course.R`. |
| Going further | Readings and IRW vignettes, each with one line on why to read it. |
| For instructors | Source (EDUC 252 slides and code), timing, what is held back and where it went, solutions status. |

If a section doesn't fit a lesson (e.g. Simulate in a conceptual lesson), don't drop
it silently. Raise it in the outline's **Open questions** and in #62; record any agreed
exception in §10.

### Length

One lesson is one class session. Target **2,000–3,000 words of prose**, excluding code
and collapsibles (the pilots run 2,200–2,650). Over length: move material into
collapsibles or *Going further* first. Splitting is a curriculum change (§1).

## 4. Threads

A thread is an idea introduced in one lesson and returned to in later ones (e.g.
specific objectivity, introduced in `rasch`, shown failing in `1pl-to-4pl`).

- **Record.** `lessons.yml` has a `threads:` list; each entry has `id`, `idea`,
  `introduced` (a lesson id) and `returns` (a list of `{lesson, how}`).
- **Display.** The header box shows "Starts threads" and "Picks up threads", with links.
- **Check.** `check_course()` fails on an unknown lesson id in a thread, and on a
  thread that returns to a lesson that comes before its introduction in prerequisite
  order. **[pending #9: not yet implemented]**
- **Drafting rule.** Before writing a lesson, read every thread that touches it. Pay
  off each thread it owes with a **Recall** callout that links back to where the idea
  was introduced. Register any new assumption or promise as a thread.

Seed threads from the pilots are in `notes/protocol-decisions.md`; the cross-checks
(#9) settle the final list.

## 5. Content rules

### Tables (#12)

- **At most 3** IRW tables per lesson, each with a job (main example, contrast or
  failure case) given in one sentence where the table is introduced.
- **Breadth.** A table appears in one lesson only, unless the reuse is deliberate (a
  thread returning to the same data) and recorded. `check_tables.R` flags reuse.
  **[pending #12: the reuse check is not yet implemented]**
- **Tokenless CSV only.** Use only tables with a tokenless CSV on their IRW landing
  page. Redivis serves those only under 100 MB; larger datasets need a teaching
  subsample published as an ordinary IRW table (#15).
- **Citation.** Always cite and link the original data: every table is cited where it
  is introduced, with the DOI or URL of the original source from IRW biblio
  (`get_citation`), never from memory, plus a link to its IRW landing page. A
  generated **Data sources** block closes each lesson. **[pending #12: generator not
  yet written]**

### Quizzes (#1)

- **Quick checks:** 2–4 per lesson, all in *Core ideas*, one after each major
  subsection (not every subsection). None in *With real data* or *Problems*.
- **Predict-then-check:** exactly **one required**, in *With real data*, immediately
  before the output that answers it, and about the finding that section turns up.
  At most one more in *Core ideas*, tied to a widget.
- Use `quiz()` and `predict()` from `lessons/widgets/quiz.js`. Every
  wrong option's feedback says why it is wrong.

### Widgets

- 3–5 "Try it" widgets per lesson (the pilots have 3–5), each tied to
  one core idea, each followed by a sentence or two saying what the reader should
  have seen.
- Math inside OJS `md` strings isn't typeset; use words there. Quiz text supports
  `$...$`.

### Problems and solutions

- **6 problems** per lesson. Mix: derivation; real data with a twist; judgment;
  design; challenge (open problems allowed, "I don't know the answer" included).
- **Solutions** are held back, one worked solution per problem, in the gitignored
  `solutions/<id>.qmd`. Open problems get a "what we know so far" note.

### Depth components (Go deeper)

- **0–2 per lesson**, always in a collapsible callout, never in the main line.
- **Criterion: load-bearing, not merely elegant.** Go deep where many later lessons
  pick the idea up.
- Self-contained, with its assumptions stated at the top.
- The alpha lower-bound proof in `ctt-reliability` is the model.
- Agreed first target: **sufficiency** in `rasch` (factorize the likelihood so it
  depends on θ only through r; conditioning on r removes θ, which gives conditional
  ML and makes specific objectivity a theorem; converse per Andersen). The other
  candidates wait for the depth pass (#10).

### IRW vignettes and deep dives

- IRW vignettes are **linked, not embedded**, where relevant: in the text where the
  question comes up, and again in *Going further*. `check_links.R` confirms each
  linked vignette exists (#72).
- A few lessons carry a **deep dive**: a result across the whole IRW corpus. It has
  three parts: a miniature on one table in the lesson, then the precomputed corpus
  result with its code, then a pointer to the vignette. Candidates are #18–#26.
- **[pending #4]** Whether deep dives are an exception to the 3-table ceiling
  (proposed: yes, since the ceiling governs worked examples); where a deep dive sits in
  the section order; how its corpus computation is stored and frozen.

## 6. Voice [pending #3]

Write as Ben (see the `domingue-voice` skill). The rules below are the candidate rules
from `notes/voice-audit-2026-09-24.md`; they become firm once Ben marks each pattern
✓ or ✗.

- **A. First-person verdicts.** Every lesson gives at least one first-person verdict
  on the choice a practitioner actually faces (which model, which coefficient, which
  rotation). Verdict first, then the rationale.
- **B. Graded adverbs, not enthusiasm.** No *remarkable, beautiful, magic, special,
  striking, vivid*. Size claims with *fairly, quite, rather, somewhat, not especially*.
- **C. Question pivots.** A section turns on a short question the text then answers.
  No "Here is a fact that...".
- **D. No coy verdicts.** Never ask the reader to compare without saying what they
  should see. Each lesson may end its core argument with one aphorism.
- **E. State the baseline.** Say what an evaluative size word (wide, clean, high,
  typical) is compared against. The IRW usually supplies the baseline.
- **F. No softeners.** No *honest(ly), genuinely, truly*. At most one "worth
  [verb]ing" per lesson.

Already in voice, keep: verdict-first openings; the fair setup followed by a blunt
landing; "merits comment"; at most one wry aside per lesson; one concrete anchor per
lesson (chess, the Mach IV, a reading RCT, the BFI-2).

## 7. Mechanics (#5)

From what broke while building the pilots and the draft site. Source:
`notes/protocol-mechanics.md`.

**Working in the repo**
- Each session works in its own git worktree, one per issue, outside Dropbox:
  `git worktree add -b <issue>-<slug> ~/worktrees/irw-course-<issue>-<slug> origin/main`.
  Push the branch; merge to `main` when the work is ready for Ben. The Dropbox
  checkout stays on `main` for Ben.
- Stage explicit paths, never `git add -A`. Use lowercase file names (Dropbox's
  case-insensitive sync turns `_TEMPLATE.md` vs `_template.md` into a conflict copy).

**Code**
- The lesson's R code lives in `lessons/code/<id>-sim.R` (the simulation) and
  `lessons/code/<id>-irw.R` (the real data), as a single source that readers can also
  download. The page includes the sim file into a webR cell, and reads the irw file's
  `## ---- label` chunks with `knitr::read_chunk`.
- The first chunk of every lesson runs `source("_course.R")`. It registers the knitr
  engine that passes `{webr}` cells through; without it, knitr silently drops the
  cells or strips `context: setup`. Every webR cell comes after it, and no cell needs
  `#| echo: true`.

**webR**
- Lessons using `mirt` include `code/_webr-setup.R` (generated by
  `webr/build_repo.R`). Others install their own packages in a `context: setup` cell
  and set `options(mc.cores = 1)`, because `parallel::mclapply` hangs in webR.
- webR has no system `tar`: use `untar(..., tar = "internal")`.
- Keep browser simulations to seconds, not minutes, and say how to scale them up
  locally. The first run of a `mirt` page takes 20–30 seconds; say so in Simulate.
- `lessons/widgets/webr-run-guard.html` (included for every lesson via
  `lessons/_metadata.yml`) replays a Run click that arrives before the editor exists.
  **[pending #13]** On some loads the editor never initialises on pages that also
  carry OJS widgets or math; until #13 closes, run the browser check three times.

**Widgets and quizzes**
- Widget math goes in `lessons/widgets/irt.js` (shared, pure functions). Add new
  helpers there rather than inline in a lesson.
- Widget colours come from `palette` in `irt.js` (`main`, `contrast`, `light`,
  `guide` for dashed reference lines, …), never a colour literal in the lesson (#71).
- Simulated samples in widgets use the seeded `rng(seed)` from `irt.js`, so the
  picture is stable on reload and changes only when a control moves.
- Math inside OJS `md` strings isn't typeset: use words there. Text passed to
  `quiz()` and `predict()` may use `$...$`.
- Check every number a quiz or predict-then-check states against the widget (run
  its code in node) or the real-data output.

**Data and citations**
- Read version-pinned CSV URLs from `irw_csv_url()`. Drop all-missing respondents.
- Before using a table, read its processing notes (`get_processing_notes`, IRW MCP
  server): e.g. `gilbert_meta_9` turned out to have waves.
- Check keying and waves before item analysis or FA: the Mach IV arrives unkeyed and
  the BFI-2 keyed, and neither says so in its metadata.
- Citations come from IRW biblio (`get_citation` via the IRW MCP server, or the
  landing page), never from memory: two first-draft pilot citations were wrong.
- Item text needs a Redivis login. **[pending #63]** Proposed: a stored snapshot
  with a provenance manifest.
- `mirt` parameterizations differ from the lesson's notation (e.g. `d` is an
  easiness): say so where the code converts.

**Render and publish**
- `freeze: auto` caches the empirical results in `_freeze/`, which is committed.
  Render with no IRW token. The first render fetches data, and a transient network
  error (`Error in scan()`) can fail it: re-run.
- Publishing is by hand, never on push: the **Run workflow** button on
  `.github/workflows/publish.yml`, or locally
  `quarto publish gh-pages --no-prompt --no-render`.

## 9. Review checklist (#5)

A lesson moves to `status: done` only when every box is ticked.

**Structure**
- [ ] H2 sections present and in the order of §3.
- [ ] 2,000–3,000 words of prose (code and collapsibles excluded).
- [ ] Every core idea from the outline is taught; anything dropped is recorded in the
      outline.

**Threads**
- [ ] Every thread this lesson owes is paid off with a Recall callout linking back.
- [ ] Any new promise or assumption is registered as a thread.

**Content**
- [ ] At most 3 tables, each job stated in one sentence; none reused outside a recorded
      thread.
- [ ] Every table cited from IRW biblio, with a landing-page link; Data sources block
      present.
- [ ] 2–4 quick checks in Core ideas; exactly one predict-then-check in With real data.
- [ ] 6 problems covering the mix; 6 worked solutions in `solutions/<id>.qmd`.
- [ ] 0–2 depth callouts, collapsible, self-contained.
- [ ] Every claim in With real data matches the rendered output.
- [ ] Issues with the data are noted gently, never as criticism of the data or its
      authors.
- [ ] Software behaviour and literature results are shown or cited, not just asserted.

**Voice** **[pending #3]**
- [ ] At least one first-person verdict; none of the banned words; every size word
      has its baseline.

**Data**
- [ ] Processing notes read for every table; keying and waves checked.

**Mechanics**
- [ ] Renders cleanly with no IRW token.
- [ ] `python3 tools/check_page.py <page URL> "<regex only the cell's output can
      match>"` passes on the local preview and, once published, on the live site
      (three times each while #13 is open). It clicks Run once webR is Ready, waits
      for the output and saves a screenshot for the visual check.
- [ ] No colour literal in a widget: every colour comes from `palette` (#71).
- [ ] Every widget changes its output when each control moves; seeded samples are
      stable on reload.
- [ ] Quiz and predict text with math is typeset (no raw `$`), and every number they
      state matches the widget or the output.
- [ ] The downloadable `code/<id>-sim.R` and `code/<id>-irw.R` run unchanged in local
      R and give the numbers the page shows.
- [ ] `check_course()`, `Rscript check_tables.R` and `Rscript check_links.R` pass. The
      last checks every IRW vignette and table link in the lessons (#72).

**Sign-off**
- [ ] Every open question is in #62; Ben has signed off.
